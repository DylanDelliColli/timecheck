## Outcomes

State what users should be able to accomplish and important behavior to preserve.
Give outcomes stable names so predictions and evaluation can reference them.
Agents develop technical plans, tests and independent scenarios from these outcomes.
Name the consumer surfaces each outcome reaches, such as a page, endpoint or export.

## Size and team

Size the release so validation on real inputs, or real-layout replicas, happens
within the first few hours of building. Split a large proposal into sequential
releases, each with its own acceptance: for example inputs and reading first, then
validated publishing and review, then hosted interpretation and latency. State an
expected wall-clock envelope so scope and time trade-offs are visible up front.
Default to two peers; add more only when each builder has its own disposable stack
(see Disposable stacks per builder in the operating guide),
so extra peers do not queue on one shared stack. This is guidance: the operator
owns scope and the roster.

## Taste and explicit constraints

State design requirements, examples/preferences and any locked boundaries. Label
examples as requirements or guidance. Include relevant host/service limitations.

## Real inputs and journeys

Name the real input families and their data policy. Before building, the team
needs layout-faithful inputs: synthetic replicas (invented content at realistic
size, privacy-checked) or an allowed real development set. Name who supplies
counts-only shapes of restricted inputs, and the real input the operator supplies.
If there is a held-out set, name who prepares it; it is checked for independence
against all builder-readable storage before it is frozen.

Real-journey checks:

1. Before first readiness: replicas run end to end on the hosted path at
   realistic size, measuring time and recovery.
2. Before first readiness: one real input runs through the real processing and
   review interface, in a lane whose client may open it.
3. Before acceptance: an uncoached walkthrough by the operator or a code-blind
   agent, starting from an empty state.

Held-out measurement runs at first readiness and reports aggregates only. These
checks are evidence requirements, not a scope gate. The retrospective reports when
real-input validation first happened.

## Scope boundaries

State what this release includes and excludes. If evidence suggests changing a
commitment, agents propose the change here for operator approval.

- Also in scope: beads or defect classes added deliberately though they are not
  outcomes.
- Default allowance: small fixes in code already being changed, covered by tests
  and declared at readiness. Remove or narrow it here if unwanted.
- Standing default: fixes for silent data loss in paths the release touches are in
  scope unless the operator rules otherwise. Remove it here if unwanted.
- Other findings outside the release are filed and flagged for the operator, not
  fixed in this release.

Ordinary in-scope defects need repair. Ask when ambiguous, missing or conflicting
product sources cannot support a confident prediction for each outcome. An
exclusion, deferral or changed outcome also needs a ruling: put the requirement, finding and
specific question on the release bead, name a follow-up owner and nudge the
coordinator/operator. Ask everything answerable on day one, and batch later
questions for the availability windows above, each with a recommended default.
Record the answer and its authority. Unresolved cases remain
explicit in readiness and are assessed conditionally; there is no blanket
readiness/evaluation gate or automatic touched-code principle rule.

## Interrupt policy

State how an urgent fix reaches the base branch during the build and who merges
it. By default the operator merges it into the base, and the team then merges the
base into the release branch.

## Release authority

State who merges into the release branch, who merges the release into its base,
and any main-branch, deployment and resource limits already decided. The base stays
frozen during the build except through the interrupt policy. Agents choose task
branches and their worktree arrangement within that authority. Missing merge or
deploy permission is not supplied by evaluator acceptance.

Specify the release's semantic version. After the accepted release merges into
the base, the merging coordinator creates an annotated tag at that merge commit
and publishes a GitHub pre-release. Its notes cite the exact evaluated commit,
the evaluator verdicts and any operator-approved deferrals. State whether the
tagged merge's product files match that commit and identify any differences.
The pre-release marks acceptance on the base branch; a full release marking
accompanies the operator's deployment. Tagging and publication do not grant
deployment authority.

## Release close

Whoever creates a worktree or checkout removes it: peers at unit delivery (their
persistent writing worktree at release close), reviewers once the review is
posted, evaluators at teardown and coordinators at lane close. Review checkouts
live under the session's temporary area, never shared /tmp. Before any removal,
at a handback or at release close, check for live processes or users and for
uncommitted, unmerged or evidence-like content. Preserve and report what you find;
while anything is live or unresolved, defer the removal and name its owner.

At release close:

1. List the release's remaining worktrees and local branches, and apply the check
   above to each.
2. Remove the worktrees that are no longer in live use and delete merged local
   branches. Removing a worktree removes symlinks, never their targets. Remote
   branch deletion follows the release authority.
3. Evidence retention: keep the final round's evidence, and retain or relocate any
   earlier artifact that a retained report or receipt references, keeping its
   durable link and hash. Drop only unreferenced superseded rounds after
   acceptance, unless this brief says otherwise.
4. Post a close receipt on the release bead listing what was removed, what was
   preserved or deferred and why, with owners. Afterwards only live work's
   worktrees remain.

## Engineering handoff

The team records these execution details on the release bead; they do not require
the operator to design the implementation:

- Before building, name the tracker/primary publication owner; verify publication
  and any unpublished state at readiness without taking over another checkout.
- Use templates/state.md for a maintained release notes record (candidate, source
  hashes, rulings, slot IDs, round, findings/owners and next action), with one named
  keeper. Fresh/reset agents read it first; decisions remain on the release bead.
- Keep one child slot bead per serialized resource, including the model sign-in.
  Only the taker checks, conditionally claims with complete notes and re-reads;
  coordinators take for their own lanes, never grant between peers or relay “free”.
  Assignee is the holder; notes carry purpose, since, candidate, grant, users,
  advisory queue and handback receipt. Teardown or explicit transfer of remaining
  resources precedes handback, never time or silence. This is advisory, not a lock.
  The retrospective records observed overlaps (target zero), whether current state
  was readable without reconstructing comments, and stale-state/receipt failures.
  Next-release use supplies this evidence, not the package change alone.
- For serialized shared-stack work, keep one slot record and direct handoff.
  Completion/teardown or a coordinated ownership handoff transfers it, never time
  or silence.
- Readiness predicts each outcome per consumer surface it names. A PASS cites a
  composed real-wire check of every such surface; deterministic-code and
  model-quality confidence are predicted separately; a prediction without
  per-surface evidence is conditional.
- Readiness includes Scope questions: requirement/finding, follow-up owner,
  ruling/source or UNRESOLVED, and the effect on the outcome prediction. Known
  failures and unresolved cases cannot silently become unconditional PASS.
- Evaluation is incremental during the build: one lane, on changed surfaces and
  the real-journey checks. The two-lane evaluation runs once, on the final
  candidate, unless a repair changes it materially. Deterministic suites run once
  per candidate; publish their commands, logs and artifact hashes for evaluators to
  verify. The retrospective reports two-lane rounds and evaluation time.
- Link one canonical run-information record per evaluation round. Update it when
  facts change and send the changes to affected evaluators after their initial
  product-source reading. Keep it on a round child bead with one named keeper.
  Put reports and structured launch/readiness-correction receipts there, and
  take/handback receipts on slot beads (templates/state.md). Corrections append
  once, reference actual comment IDs and preserve original times.
- Deliver results and the prediction-versus-verdict comparison explicitly, then
  collect independent retrospective answers and study useful Jot lessons. Keeping
  no new memories is valid. Feedback does not grant merge/deployment authority.
- For evaluator connector controls, record requested endpoints/plugin disables,
  observed effective tools and authentication, and inherited-connector mismatches
  before use. The retrospective links that next-live-launch evidence and any
  unresolved limits; configuration previews alone do not verify the tool surface.
- The retrospective reports these measures, counted from tracker timestamps and
  session logs, never estimated: sessions, resets and compactions per peer, and
  any session that outlived its claimed unit or first compaction; coordinator
  directives to peers (target zero); helper-caused incidents (target zero); peer
  requests to coordinators; time to first ready; pull-request review turnaround;
  and idle time spent waiting on a ruling that could have been asked earlier or
  parked (target zero). Handoff quality at resets is assessed from the recorded
  handoffs, and predicted versus evaluated results are compared per consumer
  surface. Also report rough notes, study passes and process captures per agent,
  and any repeated problem a remembered fact prevented. These are observations,
  not quotas or success measures.
